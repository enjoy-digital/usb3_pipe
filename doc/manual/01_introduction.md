# Introduction {#introduction}

This chapter says what USB3-PIPE is, why it exists, what it does and what it does not do. It ends
with the layout of the repository and a map of the manual. Every reader should start here.

## What the project is {#intro-what}

USB3-PIPE turns an FPGA into a USB 3 device with no USB chip on the board. The FPGA transceivers
connect directly to the USB 3 connector, and everything else runs in the FPGA fabric. The project
supports USB 3.2 Gen 1x1 (SuperSpeed, 5 Gbps) and Gen 2x1 (SuperSpeedPlus, 10 Gbps).

The project has two parts, shown in the figure below. The PHY (`usb3_pipe`) wraps the transceiver
and trains the link. It hands a clean stream of symbols to the device core (`usb3_core`), which
implements the link layer, the protocol layer, the endpoints and ready-made device classes. Both
are written in Python with Migen and LiteX, and generate Verilog for the FPGA tools.

![The project at a glance: the PHY trains the link on the FPGA transceiver; the device core turns
the symbol stream into endpoints and device classes.](project_overview.svg)

The PHY can also be used alone. Any other link layer can sit on its link interface, in a LiteX
design or as a standalone Verilog core generated by `usb3_pipe_gen` (see
[Integration](#integration)).

## Why an FPGA-only USB 3 {#intro-why}

The usual ways to add USB 3 to an FPGA board all need an extra chip:

- an external PHY, such as the TI TUSB1310A, which leaves the link and protocol layers to the
  FPGA but needs many pins and a dedicated PCB layout;
- a USB to FIFO bridge, such as the FTDI FT60x, which hides USB entirely behind a parallel bus
  but fixes the device class and limits the throughput;
- a USB peripheral controller, such as the Infineon EZ-USB FX3, which runs its own firmware on
  its own processor.

USB3-PIPE needs only a transceiver and a connector. The bill of materials shrinks, the device
class is whatever the gateware implements, and every layer can be observed and changed.

Any board with a 5 Gbps transceiver can become a USB 3 device, as long as one lane reaches a USB
connector. The lane can be routed to the connector directly, or through an SFP cage or a PCIe
edge and an adapter board.

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| Speeds | Gen 1x1 (5 Gbps) on every supported FPGA; Gen 2x1 (10 Gbps) on Kintex UltraScale+ GTY; Gen 1x2 in simulation |
| PHY | LFPS, training sequences, 8b/10b and 128b/132b coding, scrambling, clock compensation, polarity, LTSSM with Recovery, U1, U2, U3, Hot Reset, Warm Reset, Compliance and Loopback |
| Link layer | Header packet flow control, retries, link management packets, timers, SuperSpeedPlus operation |
| Protocol layer | Control endpoint, Bulk IN and OUT with bursts, Isochronous IN, U1 and U2 power management (option) |
| Device classes | Vendor Bulk, CDC-ACM serial port, UVC camera (Bulk or Isochronous), Mass Storage (block RAM or DRAM), composite devices |
| Datapath | 32-bit link words at 125 MHz, or 64 and 128-bit words for Gen 2 bandwidth and slow fabrics |
| Host drivers | Standard Linux drivers: usbfs, `cdc_acm`, `uvcvideo`, `usb-storage` |
| Debug | Link state history and counters, transceiver controls, header packet and link traces, LiteScope probe groups |
| Verification | Python host model, unit and system tests, Verilator simulation of host, PHYs and device |

## Status {#intro-status}

The project is validated on hardware with a Linux xHCI host. The table below gives the headline
Bulk throughputs of the bandwidth example, in MB/s, with the data checked on both sides.

| Board | Speed | Bulk IN | Bulk OUT | Full duplex |
|-----------------------|----------|---------|----------|-----------------|
| Acorn CLE-215+ | Gen 1x1 | 446 | 449 | 376 + 400 |
| Alibaba XCKU3P | Gen 2x1 | 744-785 | 873-881 | 619 + 736 |
| Tang Mega 138K Pro | Gen 1x1 | 372 | 433 | 262 + 383 |
| ECPIX-5 | Gen 1x1 | 434 | 449 | 342 + 349 |

The Gen 2x1 figures use the 64-bit link interface; the range of the XCKU3P board depends on the
max burst. The Tang Mega 138K Pro and the ECPIX-5 run their link layer on 64-bit words, at
62.5 MHz and 83.33 MHz. On the Acorn and on the XCKU3P board, full duplex runs of more than 130 GB end with no
data error and no Recovery. On the Acorn, Linux autosuspend and resume (U3) is validated as well.
[Performance and resources](#performance) gives every measurement.

## What it is not {#intro-limits}

The project is a USB 3 *device*. It does not implement a host, a hub or a USB 2 fallback: the
USB 2 pair of the cable is left unused, so the host must have a working SuperSpeed port.

Other limits of the device core:

- Gen 2x2 is not implemented, and Gen 1x2 runs in simulation only.
- Bulk, Control and Isochronous IN endpoints are supported. Isochronous OUT and Bulk Streams are
  not.
- U1 and U2 are rejected by default; with the `with_lpm` option they are accepted, validated in
  simulation only. U3 (suspend) is validated on hardware.
- Function remote wakeup, latency tolerance messages and precision time measurement are not
  supported.
- The 64-bit and 128-bit link interfaces serve the Bulk endpoints, and the Mass Storage and
  CDC-ACM classes through endpoint converters; the UVC class and the Isochronous endpoint stay on
  32-bit words (see [Endpoint converters](#core-converters)).

## Repository layout {#intro-layout}

| Path | Content |
|---------------------|------------------------------------------------------------------------|
| `usb3_pipe/` | The PHY: transceiver wrappers, LFPS, training, coding, scrambling, datapaths, LTSSM, debug, standalone generator |
| `usb3_pipe/gw5/` | Register configurations of the Gowin GTR12 transceiver |
| `usb3_core/` | The device core: link and protocol layers, endpoints, descriptors, device classes, traces, host model |
| `bench/` | Board targets, the shared SoC and the host-side tools (bandwidth, loopback, traces, soak) |
| `examples/` | Configuration files of the standalone Verilog core |
| `test/` | Unit and system tests (pytest) |
| `sim.py` | Verilator simulation of a host model, two PHYs and the device core |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`) and the board photos |
